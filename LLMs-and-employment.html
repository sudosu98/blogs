LLM's and Employment?

Aug 21, 2025

Welcome to the age of LLMs. Half the population thinks LLMs think just because they implemented a <Loader/> after every prompt that says “thinking...”. I’m not going to lie— it does give the appearance of thinking.

Thinking - ideas or opinions about something.

AI Development = Speed + Thoughtful decisions? In my opinion, using AI in my development life cycle did drastically improve at least one of the two while often contradicting each other. What I mean by this is, I often found myself being fast with it or being thoughtful with it and not both. So the balance was missing.

Have you ever had a super junior intern working under you, and no matter how much you explained, they’d just not understand? It’s not because you cannot explain it well enough, nor because they are dumb enough to not understand. It’s just that their brain has not yet been exposed to the problem at hand — and it is way above their current understanding of software.

That is somewhat how I see LLMs today. They can produce an answer that looks incredibly confident and sophisticated, while still getting the underlying problem completely wrong.

In order to make these systems more useful, people started using RAG, fine-tuning, reinforcement learning, tool use, and so on. But these are not really the same thing.

RAG gives the model access to external information at inference time. Fine-tuning changes the model itself by training it further on additional data. Reinforcement learning uses feedback or reward signals to optimize behaviour. They can all improve the usefulness of an LLM, but in very different ways.

And yes, at the foundation, an LLM is trained to predict tokens. But I don't think saying “it's predicting, not thinking” completely explains what is happening anymore.

Modern LLMs can generate intermediate reasoning steps, use tools, retrieve information, write code, execute code, inspect the result and try again. Whether we call that “thinking” or extremely sophisticated prediction is almost a philosophical argument at this point.

What matters to me is whether I can trust the result.

The reason LLMs can sometimes appear to have emotions or personality is also more complicated than simply having “high-level English grammar”. They learn statistical patterns from enormous amounts of human-generated data, including the way people express emotions, uncertainty, confidence, humour, sarcasm and personality.

So when I ask an LLM to be controversial and it responds with “Got it 😏”, it isn't necessarily experiencing amusement or excitement.

It's producing a response that is statistically appropriate to the context I gave it.

When I asked ChatGPT to fix the above paragraph and asked it to keep it controversial, it started with "Got it 😏"!

With all that being said, how is the employment scenario looking? OpenAI launched its ₹399/month plan in India in August 2025. Why is that interesting? Let's do a hypothetical calculation — not because it will tell us exactly how much an AI company spends, but because it gives us an idea of the scale involved.

Definitions :

Parameters, precision, KV cache, FLOPs, latency, energy
  • Weights: the stored parameters of the model.
  • KV cache: attention-related state stored while generating tokens, allowing the model to avoid recomputing previous context.
  • FLOPs: floating-point operations. A rough dense-model estimate used below is 2 × parameters × tokens.
  • Latency: the time required to process a request. Actual latency depends heavily on architecture, batching, parallelism, memory bandwidth and utilization.
  • Energy: power × time, expressed here in Wh.

Selected configuration :

Model 4.0 × 1012 params (4T) — hypothetical
Weights precision INT8 (1 byte / weight)
KV cache precision FP16 (2 bytes / element) — illustrative
Tokens (prompt / gen) 4,000 in / 500 out → 4,500 total
Hardware H100 SXM 80 GB — illustrative hardware
Compute assumption 400 TFLOPS / GPU effective throughput — illustrative only
Power / GPU 600 W — illustrative operating point
Sharding Ideal linear sharding — intentionally optimistic

Calculations :

Weights:

4,000,000,000,000 weights × 1 byte = 4,000,000,000,000 bytes ≈ 4 TB

KV Cache:

This is where things become architecture-dependent.

A simplified KV-cache calculation is:

KV ≈ 2 × layers × KV_heads × head_dim × sequence_length × bytes

The important part here is KV_heads, not simply the number of attention heads. Modern architectures can use techniques such as Grouped Query Attention (GQA), where the number of key/value heads is smaller than the number of query heads.

Therefore, assuming “80 layers × 128 heads × 128 head_dim” for a hypothetical 4T model would give a very specific number without actually knowing the model architecture.

For that reason, I won't pretend the KV cache is exactly 11.8 GB. The real number depends on the architecture, context length, precision and number of concurrent requests.

Important: the 4 TB weight requirement is much more robust than any specific KV-cache estimate here.

Theoretical weight-only GPU count:

4,000 GB ÷ 80 GB ≈ 50 H100 GPUs

But 50 GPUs is only a theoretical lower bound for the weights. A production system needs additional memory for KV cache, activations, runtime buffers, communication and concurrent users.

So the real number of GPUs required to serve a model cannot be inferred from parameter count alone.

Compute:

For a rough dense-transformer estimate:

FLOPs ≈ 2 × parameters × tokens

2 × 4T × 4,500 ≈ 36 × 1015 FLOPs = 36 PFLOPs

This assumes a dense model where all 4T parameters participate in every token. An MoE model with 4T total parameters could activate only a fraction of them for each token, making this estimate substantially different.

And this is where the original calculation gets tricky:

It is tempting to say:

36,000 TFLOPs ÷ 23,200 TFLOPS ≈ 1.55 seconds

But this should not be interpreted as actual end-to-end request latency.

Theoretical FLOPS are not the same as real LLM inference throughput. Memory bandwidth, GPU utilization, communication overhead, parallelism, batching and the difference between prefill and decode all matter.

For example, an H100 SXM has 80 GB of GPU memory and up to 3.35 TB/s of memory bandwidth, while its advertised tensor-core throughput depends heavily on numerical precision and sparsity.

So the 1.55 second number is better understood as an idealized arithmetic lower-bound-style calculation, not a production latency estimate.

Energy:

If, purely for the sake of the hypothetical calculation, we assume 58 GPUs operating at 600 W for 1.55 seconds:

Energy = 58 × 600 W × 1.55 s

≈ 53,736 J ≈ 14.9 Wh

Again, this is not a measurement of a real ChatGPT request. It inherits all of the assumptions above.

With all these calculations, according to commonly cited figures India produces around 1.5 million engineering graduates every year. But rather than assuming that half of them actually subscribe to an AI service and send exactly 100 requests every day, let's treat the following as a deliberately exaggerated scenario just to understand scale.

Scale Calculations :

Hypothetical Users:
1,500,000 engineers × 50% = 750,000 hypothetical users
Hypothetical Daily Volume:
750,000 users × 100 requests/day = 75,000,000 requests/day
Energy Scenario:
If we use a hypothetical average of 0.3 Wh/request:
75,000,000 × 0.3 Wh = 22,500,000 Wh = 22.5 GWh/day
Why use a scenario instead of the earlier 14.9 Wh?
Because the 14.9 Wh figure came directly from an intentionally extreme 4T-model calculation with idealized GPU assumptions. It should not be treated as a measured energy cost for a production chatbot request.
Actual inference energy varies substantially with model architecture, prompt length, output length, reasoning effort, batching, hardware, utilization and serving software.
Electricity Cost Scenario:
At $0.12/kWh:
22,500 kWh × $0.12 = $2,700/day
This is only the electricity component and does not include the cost of GPUs, networking, cooling, data-centre infrastructure, staff, depreciation or other operating expenses.

The interesting part isn't really whether the number is 1 GWh, 10 GWh or 20 GWh. The interesting part is that inference at massive scale creates a completely new industrial demand for electricity, compute, networking and data-centre infrastructure.

My instinct is that AI will create an artificial demand for energy that pushes up the natural baseline of consumption. In the short run, this could put pressure on grids and generation capacity, especially in regions where data-centre demand grows faster than new supply.

But there is another side to this.

Over time, the cost of a unit of inference should fall as hardware, model architectures, quantization, batching and serving systems improve. We have already seen how quickly the cost of computation can change when an industry starts optimizing around a workload.

And this brings me back to employment.

If the cost of producing software keeps falling, companies don't necessarily have to choose between “same work with fewer engineers” and “same engineers doing the same work”.

They can simply build more.

An engineer who previously took four hours to implement a feature might now produce the first version in thirty minutes with AI assistance. That does not automatically mean the company needs 87.5% fewer engineers. It could mean the company expects more output from the same team.

Of course, some of the productivity gain can also translate directly into fewer people being required for certain tasks.

And this is where things get uncomfortable.

Current evidence suggests that the impact is likely to be uneven. Routine programming work is easier to automate than architecture, debugging, product decisions, system design and work that requires responsibility for the final outcome.

The U.S. Bureau of Labor Statistics currently projects software developer employment to grow by 15.8% from 2024 to 2034, while computer programmer employment is projected to decline by 6% over the same period.

That's an interesting distinction.

Maybe the market isn't asking:

“Do we need people who can write code?”

Maybe it is increasingly asking:

“Do we need people whose primary value is writing code?”

Those are two very different questions.

And that is why I don't think the answer is simply “AI will replace engineers”.

I think AI will replace some tasks, change the expectations of engineers and potentially shrink some categories of jobs while creating demand for others.

The engineer who only knows how to write boilerplate code may become less valuable.

The engineer who understands the system, can judge whether an AI-generated solution is correct, can make architectural decisions and can take responsibility when something breaks may become considerably more valuable.

Just as cloud computing created entirely new roles while automating parts of traditional infrastructure work, AI will likely do something similar to software development.

Some jobs will disappear.

Some will shrink.

Some will become more valuable.

And some jobs will appear that we don't even have names for yet.

The real challenge is to stay in sync with this progress — making sure AI remains a friend, not a foe, supporting us without making us obsolete in the process.

Maybe AI isn't replacing engineers.

Maybe it is replacing the unit of work.

A software engineer used to be hired to produce code. Increasingly, they may be hired to produce outcomes.

That's a subtle but massive difference.

If AI makes implementation cheap, then judgement becomes more valuable.

And if generating code costs almost nothing, the expensive part becomes knowing what to build, why to build it, whether it is correct, whether it is secure, whether it scales, whether users actually need it — and who is responsible when it breaks.

That's engineering.

So learn AI.

But don't stop there.

Learn systems. Learn databases. Learn networking. Learn security. Learn product. Learn how to debug something that doesn't have an obvious answer.

Learn how to look at an AI-generated solution and say:

“This is wrong.”

And more importantly:

“Here's why it's wrong.”

NOTE : The calculations above are intentionally hypothetical. They are meant to demonstrate the scale of LLM inference, not to estimate the actual architecture, GPU count, latency, electricity consumption or cost of any particular commercial AI service. The employment outcome is also not predetermined. AI is likely to automate some tasks, augment others, and create entirely new categories of work. The important question is not whether every engineer will lose their job, but whether the skills that make an engineer valuable will change.
